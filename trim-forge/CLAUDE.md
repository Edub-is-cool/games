# Trim Forge

## Overview
A Minecraft **Java Edition armor trim previewer**. Pick a trim pattern and trim material, put it
on any armor from leather to netherite, and see the result on a pixel-art figure. Every piece is
configured **independently** — the helmet can be turtle scute with a Tide/diamond trim while the
chestplate is diamond with Silence/amethyst and the boots are bare iron. It also emits the
matching `/give` commands.

Not a game — a tool. It lives in the games portfolio because it shares the same static,
zero-dependency setup.

## Textures — read this first
The previewer renders **the game's own textures**, not an imitation of them. An earlier version
used hand-drawn pixel art and it read as "a pattern on armor" rather than a trim, because real
trims are sparse accents in fixed places (collar, waist, knee, boot cuff) at roughly 10% coverage.

`textures.js` holds 71 textures inlined as base64 data URIs (~13.9 KB of PNG, ~22 KB of file),
generated by `tools/extract-textures.py` from a Minecraft client jar:

```bash
python3 tools/extract-textures.py ~/Library/Application\ Support/minecraft/versions/26.2/26.2.jar
```

They are inlined rather than shipped as loose files because the palette swap needs
`getImageData`, and Chrome taints a canvas that has drawn a `file://` image — loose PNGs would
break the "just open index.html" convention the rest of the portfolio follows.

**These are Mojang's assets.** The page carries attribution and a not-affiliated notice in the
footer. Keep both if you touch the footer. If they ever need to come out, the swap is small: drop
`textures.js` and read the same paths from a file the visitor supplies.

Regenerating against a newer jar picks up new content automatically — copper armor, the resin
trim material and turtle scute all arrived this way.

## Views
Two renderers share the same textures:

- **3D** (`render3d.js`) — a hand-written WebGL viewer, drag to rotate and scroll to zoom.
  Six body boxes, the skin's outer layer, one inflated box per armour piece, plus cape and
  elytra. No libraries.
- **Flat** (`render.js`) — the original front-on 2D view. It still draws **every picker
  thumbnail**, which is why it has to stay: 38 WebGL contexts would blow the browser's limit.

Cape and elytra are 3D only — they are behind the figure and invisible head-on.

## Skins and capes
Drop a PNG on the stage, or use the buttons under the preview. Skins are normalised to a
64-wide canvas (`normaliseSkin`), so 64x64, legacy 64x32 and HD skins all end up in the same
coordinate space and every UV rect keeps working. Legacy skins have no left limbs, so those
mirror the right ones (`bodyFaces`, `bodyBoxes`). Slim arms are a toggle — a PNG can't tell you.

Both are kept in `localStorage` under their own keys, separate from the set.

Cape textures are **not in the game files** — Mojang serves those per account, so there is
nothing to extract and none ship here. A cape PNG is 64x32 and carries the elytra artwork in the
same file, which is why an equipped elytra can render from it.

## Model notes worth keeping
- Armour inflates by **1.0** for helmet/chestplate/boots and **0.5** for leggings, matching the
  game, so the layers never z-fight.
- `boxGeometry` bakes a per-face brightness rather than lighting anything.
- Boxes written in Minecraft's model space face -z; `yaw180` turns such a box around. The **cape
  needs it, the elytra does not** — the wing's visible surface is the box's *back* rect and its
  inner face is fully transparent. Getting this backwards points the wings the wrong way.
- Both elytra wings span the full back (x -5..+5) and splay apart by rotation; they are not
  offset out to the sides.
- An elytra takes the chestplate slot and replaces the cape, as in game.

## Tech Stack
- **HTML5 Canvas** — the figure and every picker thumbnail
- **CSS3** — three-panel layout, collapses to one column on mobile
- **Vanilla JavaScript** — no build step, no dependencies (matches `ore-bit/`, `emoji-battle/`)
- **WebGL** for the 3D view — hand-written, no libraries
- `localStorage` remembers the set (`trim-forge-state-v3`), skin and cape

## How the render works
The figure sits on a **16×32 grid** with 1 cell of padding. Faces are sampled from the standard
armor UV layout (64×32) and the player skin (64×64), then blitted to their spot on the grid:

```
head x4,y0    body x4,y8    arms x0/x12,y8    legs x4/x8,y20
```

Armor textures carry **one** arm and **one** leg, mirrored for the far side, exactly as the model
does — hence the `mirror` flag in `PIECE_SPEC`.

The two armor layers split by piece, which is what makes per-piece mixing work — the regions are
disjoint, so each piece can be drawn from its own material's texture:

| Piece | Layer | Texture rows it occupies |
|---|---|---|
| Helmet | `humanoid` | head y8–15 (face opening at y11–13) |
| Chestplate | `humanoid` | body y20–31, **arm y20–26 only** |
| Boots | `humanoid` | leg y26–31 |
| Leggings | `leggings` | body y27–31 (waist), leg y20–28 |

**Bare forearms below the chestplate are correct** — the sleeve genuinely stops at y26. Don't
"fix" it. Draw order is leggings → boots → chestplate → helmet so the skirt and cuffs layer the
way they do in game.

## Trim colouring
Trim textures ship greyscale, keyed to `palettes/trim_palette` (8 pixels). `trimTexture()` maps
each keyed colour to the same slot in the chosen material's 8-pixel palette — the game's own
mechanism, so the colours are exact rather than eyeballed. Results are cached per
pattern+layer+palette.

A trim whose material matches its armor uses the game's real `_darker` palette (`DARKER_PAIRS`),
not an approximation. Only copper, iron, gold, diamond and netherite ship a darker variant.

Leather is greyscale and gets multiplied by the dye colour, then `leather_overlay` is drawn
un-tinted on top — the same two-texture trick the game uses.

## Behaviour worth preserving
- **Per-piece everything.** Never collapse state back to one global armor/trim; mixed sets are
  the point. "Apply piece to all" covers the matching-set case, and skips a material that isn't
  legal for a slot.
- **`pieces` on a material restricts it to slots** — turtle scute is helmet-only, and both the
  armor picker and `drawPiece` respect it.
- **Pickers are live previews.** Every swatch renders the *currently selected piece* with that
  option applied, cropped by `PIECE_CROPS`. Adding an option means adding data, not markup.

## Give commands
- **1.21.5+** components — `/give @p minecraft:netherite_chestplate[minecraft:trim={pattern:"minecraft:sentry",material:"minecraft:copper"}]`
- **1.20.4** NBT — `/give @p minecraft:netherite_chestplate{Trim:{...}} 1`

Leather adds `minecraft:dyed_color=<int>` (or `display:{color:<int>}` on 1.20.4). Gold's item id
prefix is `golden` and turtle's is `turtle`, which is why `ARMOR_MATERIALS` carries a separate
`item` field alongside `tex`.

## Template data
Each pattern records where its smithing template is found, its duplication material and the
version it was added (1.20 for the original 16, 1.21 for Flow and Bolt). Flow duplicates with a
Breeze Rod — the only trim that duplicates with an item rather than a block.
